# Bore & Barrel

A dummy gunshop storefront built as a Progressive Web App. It runs offline
with an app shell, a web app manifest, and a service worker, and uses React +
Vite + Tailwind CSS.

The storefront is an academic demo: cart checkout is labeled as a simulation
and opens WhatsApp with a prefilled demo-only message. An optional
`VITE_WHATSAPP_NUMBER` can target a WhatsApp number; when it is unset, WhatsApp
opens its recipient picker.

## Setup

```bash
npm install
npm run dev      # dev server with HMR
```

Other scripts:

```bash
npm run build    # production build to dist/
npm run preview  # serve the production build
npm run lint     # oxlint
```

## Catalog backend fields

The Supabase `products` table must include `deleted_at` and `image_urls` for
soft-delete/restore and multi-image catalog support. Existing products remain
visible when `deleted_at` is `NULL`.

```sql
ALTER TABLE public.products
  ADD COLUMN IF NOT EXISTS deleted_at timestamptz,
  ADD COLUMN IF NOT EXISTS image_urls text[] NOT NULL DEFAULT '{}';

UPDATE public.products
SET image_urls = ARRAY[image_url]
WHERE image_url IS NOT NULL AND cardinality(image_urls) = 0;
```

The non-Supabase REST backend should accept `page`, `limit`, `search`,
`category`, `sort_by`, `order`, and `include_deleted` on `GET /api/v1/recipes`,
and support `PATCH /api/v1/recipes/:id` with `deleted_at` set to a timestamp
or `null`. `DELETE /api/v1/recipes/:id` is reserved for permanent deletion.
Catalog query results are cached in memory for 30 seconds; changes invalidate
that cache. Catalog uses numbered page navigation (6 products per page) and
product images use native lazy loading.
Catalog items can also be saved as browser-local drafts from the product card
or detail view; find, reopen, or remove them in Profile → Draft.
Product detail pages can be shared with the Share API or copied to the
clipboard. Shared links include the product ID and reopen that product detail
page when visited.

## Review management and voting

Users can edit or delete only their own review; the API must enforce the
`user_id`/`user_identifier` check on update and delete requests. Supabase
projects need a `review_votes` table with a unique `(review_id, user_id)` pair,
`vote` restricted to `1` (thumbs up) or `-1` (thumbs down), and a foreign key
to `reviews.id`. Configure its select/insert/update/delete policies to match
the existing review access model. Existing reviews expose `is_owner`,
`thumbs_up`, `thumbs_down`, `user_vote`, and `can_vote` in the REST API.
If the Supabase table or REST vote endpoint is unavailable, the app keeps
votes in this browser's local storage; those fallback votes are not shared
between devices and are replaced by backend votes when the backend is enabled.
Non-Supabase backends should implement
`POST /api/v1/reviews/:id/vote` with `{ user_identifier, vote }`; send `null`
as `vote` to remove the current vote. Review update/delete endpoints must
validate ownership server-side.

Example Supabase table (adjust `review_id` to match the type of `reviews.id`
if necessary):

```sql
CREATE TABLE IF NOT EXISTS public.review_votes (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  review_id uuid NOT NULL REFERENCES public.reviews(id) ON DELETE CASCADE,
  user_id uuid NOT NULL,
  vote smallint NOT NULL CHECK (vote IN (-1, 1)),
  UNIQUE (review_id, user_id)
);
```
